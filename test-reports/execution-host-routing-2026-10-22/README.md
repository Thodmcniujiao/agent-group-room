# 0.14.1：执行故障宿主分流与实际输出上限

2026-10-22。已部署到本机 49315；未重启原项目任务，未调用外部生成模型。

## 本次故障的证据

- E06 第二次实际 HTTP 请求发送 `max_tokens=16384`，输入 3,786 tokens，返回输出 16,384、其中推理 16,384，最终 `output_truncated`。额度在思考阶段耗尽，没有交付代码；不是输入上下文已满。
- 该房间实际保存 `output_tokens=32768`，但旧宿主、MCP 配置校验和 HTTP 子进程把编码执行限制在 16,384。界面值与编码实际请求不一致。
- E07 达到 `max_turns (16)`，结束时已有 `main.ps1` 和 9 条写入恢复记录。9 条记录对应同一文件的多次更新，不能把每条记录理解为一次重新派发。现有文件有独立宿主验收证据，但恢复记录尚未全部核实。
- 原 `host_error=not started_execution` 把所有启动后异常都交回监工，因此上述两种运行故障也再次产生了监工请求。指纹复查逻辑还允许“错误改变”进入监工；现已修正复查路径。

## 修改范围

- 所有执行运行器/传输异常均交由宿主；正常的 `STATUS: BLOCKED`、内容问题和验收不通过仍是执行证据。异常分类保留阶段、是否已启动、输出截断、工具轮数耗尽及写入恢复原因。
- 宿主保存失败证据、文件哈希和待核实写入，独立运行原契约验收。已经通过且内容未变的完整宿主验收直接复用。已启动或启动回复丢失的契约不自动重派；“仅复查宿主”及续接短语不调用监工/执行者。恢复可证明的交付后也只结束宿主核对，本轮不追加模型调用。
- 旧版本中最近一次已知运行故障即使误标 `host_error=false`，续接时也先转宿主。历史失败记录不改写为成功。新的具体用户指令可进入正常规划，不能被误当成重复执行原契约。
- `gui/executor_limits.py` 对固定版本依赖作局部、可复现的输出参数适配，MCP 配置与隔离 HTTP 子进程统一接受房间显式预算。移除隐藏 16K 截断；范围仍为本应用原有的最高 128,000。依赖安装目录、原默认值及进程/写入/取消/响应字节边界不修改。HTTP 子进程保留无 HOME/USERPROFILE 的隔离环境。
- 参数位置：“此协作室的上下文设置 → 输出预留 / API 输出上限”；工具续轮在相邻字段独立设置，默认 16、范围 1–100。两处增加功能与原理链接，解释思考计量、请求输出上限与工具续轮的差别。

截至当日，[DeepSeek 官方参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)允许 `max_tokens` 最高 393,216；这是服务商范围，本应用范围独立，也不能推定其他兼容服务支持同值。提高输出上限提供生成空间，不保证任务必定在该额度内完成，不改变推理强度。
