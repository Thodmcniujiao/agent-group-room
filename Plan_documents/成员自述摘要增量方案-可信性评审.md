### CoMem 的真实结论与方案表述的差距

| --- | --- | --- | --- | --- |
| DeepSWE 32B | 40.4 | 41.0 | **+0.6** | 1.68x / 1.45x |

## 三、内部一致性问题：成本推演案例不能成立

第四部分第四节（第 715–730 行）是全篇最需要撤回的一段。

### 3.1 与主方案基线直接冲突

主方案第 9、17 行写明：受阻阶段 1,205,819 输入 token 中，**DeepSeek 执行者约 0（启动失败）**，监工 56.9%、ChatGPT 成员 34.7%、Claude 5.7%、Gemini 2.8%。

执行者根本没起来 → 那个阶段**没有执行者 Bash 输出、没有验收输出、没有 Git 工具输出**。而案例把 1,080,000 token 的"避免量"主要记在 E7（拦截命令输出）和 E1（压缩 pytest 输出）头上。这两项在那个场景里能省的量接近 0。

真正的成本来源是监工每轮重放完整历史（56.9%）和成员全文互读（34.7%），也就是 C1/C3/S2 那条线。**案例的因果归因和它引用的基线数据是相反的。**

### 3.2 与 E1 自己的字符上限不自洽

E1 的前提是"现在 Bash 输出最多 50,000 字符、验收 30,000、Git 40,000"。
- 50,000 中文字符 ≈ 3 万 token，英文 ≈ 1.3 万 token，**单次 dump 不可能是 40,000 token**；
- "20,000 行 pytest" 在 50,000 字符上限下根本装不下（2 万行至少 40 万字符），这个数字与上限互斥；
- 要凑出 1,080,000 避免量，需要约 30–40 次"满额 dump"。在一个执行器未启动的阶段不可能发生。

### 3.3 "方案 A 23,000 token 对比方案 B 89.5%"的对比是失真的

- 第 722 行把 1,200 token 的规则按 `1,200 × 20 = 24,000` 全额计价，**没有算 Prompt Cache 折扣**。而这整篇文档的 E3 就是在讲缓存。系统提示前缀是天然可缓存的，按 10% 计价则只有约 2,400 token 等效成本。用不打折的数字去抬高方案 A 的成本，是单边比较。
- 第 729 行说"System Prompt 规则增量仅 40 Token（E5 简洁指令）"，漏掉了 S1 的 `SUMMARY_RULE`。实测该规则渲染后 116 字 ≈ **68–97 token**，而且 S1 的注释明确写着"讨论成员**每次发言**的指令末尾追加"，不是发一次。方案第 70 行把它标为"约 30 Token 单次规则"，**低报了 2–3 倍，并且"单次"的说法与代码相反**。此外每条回复多出的摘要行本身是输出 token，单价是输入的 4–8 倍。
- 结论页说"新增 Overhead 仅约 2,000 Token"，把上面两项都漏了。

### 3.4 违反本文档自己立的证据标准

- 第 283 行："节省比例由各项目自报，本系统的真实收益由 A1/E6 净节省核算为准"；
- 主方案第 19 行："本方案不承诺固定节省量，只承诺按同角色、同适配器、同任务对比"。

然后在第 730 行给出"89.5%"、在第 809 行把"云端 API 计费 Token 减少 60% 以上"写成验收通过标准。**同一份文档，前面说不承诺数字，后面拿数字当验收门槛。** 这是最伤可信度的一处，因为它让读者无法判断其他数字该信到什么程度。

## 四、E7（透明沙箱拦截）的可实施性缺陷

这是本次新增里风险最高的一项，而且默认开启（第 782 行 `'sandbox_interception': True`）。

### 4.1 生成的命令有语法错误（已复现）

第 545–552 行那段嵌套 f-string 拼出的 `python -c` 命令，编译报错：

```
SyntaxError: unexpected character after line continuation character
出错位置: ... [f\'...[跳过 {len(lines)-60} 行]...\']
```

原因是内层 f-string 的引号被写成了 `f\\\'`，渲染结果是 `f\'`。**这段代码从未运行过。** 而它一旦运行失败，执行者收到的是一个 Python traceback；按本文档自己的警告（第 77 行"复杂路由指示可能诱发模型额外规划、重试"），一次失败的拦截会引发重试循环——正好制造它想消除的 token 爆炸。

复现脚本：`Plan_documents/_check_new_claims.py`。

### 4.2 命令改写会吞掉管道和重定向

`pre_tool_hook` 用 `re.search` 命中后就 `return wrapped, ...`，**不是把匹配片段替换回原命令**。实测三种常见写法全部丢失语义：

| 输入 | 结果 |
| --- | --- |
| `cat build.log \| grep -i error` | 管道丢失，grep 不执行 |
| `cat a.txt b.txt > merged.txt` | 重定向丢失，文件不被写入 |
| `cd dist && cat runtime.log \| head -5` | 前半段丢失 |

对执行者来说，`cat a b > c` 静默不写文件是**数据损坏级**的问题，比多花 token 严重得多。

### 4.3 其他实现缺口

- `DANGEROUS_CMDS` 定义了三条规则，方法体只实现两条；`grep`/`find`/`rg` 的"全仓暴力检索"拦截在正文和验收里都被宣称，代码里没有。
- `git diff` 的改写改变了退出码语义：原命令有差异时退出码 1，改写后 `git diff --stat` 恒为 0。验收判定会失真。
- 渲染函数 `post_tool_hook` 与 E1 的 `present()` 谁先谁后没有规定。E1 的 `ensure_kept` 只保留命中 `KEEP` 正则的行和最后 40 行，而 `[宿主透明沙箱已介入: …]` 这个标记**不在 `KEEP` 里**，很可能被 E1 自己删掉——模型永远不知道输出被截断过。
- 接入层写的是 `execution_context.py`（第 569 行），但 E1 的接入点写的是 `tool_child_env.py`。按主方案 A3 的描述，执行者 Bash 跑在独立子进程环境里，在 `execution_context` 拦截很可能拦不到执行者的 Bash。

### 4.4 结论

"杜绝 95% 以上的意外上下文溢出"（第 569 行）既无测量方法，也无实现支撑。**建议把 E7 从"改写命令"降级为"后置压缩 + 危险命令拒绝"，并默认关闭。**

## 五、E8（端侧 4B 记忆）的技术可信性

### 5.1 机制被替换了，但论据没换

方案的论证是：通用小模型"写出的摘要是空洞的文学复述"（第 581 行），所以要用 **CoMem 的行动一致性 GRPO 模型**。
方案的实施是：`POST /api/generate` 给一个叫 `qwen3-comem-4b` 的 Ollama 模型，带一段 system prompt，`temperature 0.1`（第 604–647 行）。

`temperature 0.1` + system prompt 就是**普通指令模型推理**，不是 CoMem 的机制。方案的实现恰好落在它自己批评的那一类里。要么实现真的用上 GRPO 权重，要么就别拿"行动一致性训练"当理由。

### 5.2 模型产物不存在，且训练分布不匹配

- CoMem 确实开源了权重（HuggingFace `YWZBrandon/summary-sft-qwen3-4b` 及三个 GRPO 变体），但**没有 `qwen3-comem-4b` 这个 Ollama 标签**。落地要自己走 safetensors → GGUF → 量化 → Modelfile，方案里没有这一步，也没有评估 4-bit 量化对 RL 对齐行为的破坏。
- 这些权重是在 **SWE-Bench-Verified 的轨迹**上、针对 DeepSWE / GLM-4.7 / Qwen3-Coder-Max 三个主干训练出来的。本项目的输入是**中文多角色方案辩论**。分布差异很大，方案却假定它"学会 Coding Agent 最关键的记忆权重"可以直接迁移到群聊治理。这是未经检验的外推。

### 5.3 时序设计与 CoMem 的核心机制相反

论文的贡献点是 `k`-step-off **异步重叠**：记忆模型在后台压缩，主 Agent 不等它。
方案的实现是 `await` 一个 **8 秒硬超时**，超时 `return None` 静默降级（第 639–646 行）。后果：

- Ollama 冷启动加载 4B 模型常需 3–10 秒，**首次调用几乎必然超时**；
- 8 秒内的预算要覆盖 prefill（8,000 token）+ 生成（数百 token），在 4B 上很紧张；
- 因为失败是静默的，你无法从日志判断 E8 到底是"没启用"还是"一直在超时"，验收用例 10（第 808 行）测不出来。

### 5.4 与主方案的治理不变量冲突（最严重）

主方案的边界是"成员之间的公开原文由宿主直接投递"、"模型摘要不能创造批准与表态"（主方案第 23–26 行）。S1 的摘要是**作者自述**，所以能标"作者自述摘要"并在第 122 行声明"不能作为批准、表态或证据"。

E8 的记忆块是**宿主小模型对多个成员的二次综述**，既不是作者原文，也不是作者自述。它被注入监工 payload（而监工正是算共识的那一方），却没有任何一条规则禁止把它当表态依据。第 122 行那条保护只覆盖 S1。

具体风险：一个 4B 模型把"甲基本同意但有保留"揉成"甲同意"，监工据此算共识 → 这正是第 118 行警告的幻觉，只是从摘要搬到了记忆块。

另外，记忆块**没有绑定方案版本哈希**。主方案 B2 让批准绑定 `(plan_id, version, sha256)`；E8 的状态块可以跨版本存活，被否决的旧提案可能借记忆块"复活"。

### 5.5 收益空间可能已经被 C1 吃掉

E8 定位是"会话 20–50 轮、历史破 100K token"。但 C1 已经给监工单轮输入设了上界，S2 也在预算内用摘要替代。E8 能压缩的，只剩下 C1 之后仍然超预算的部分。方案没有用 A1 数据证明"实施 C1 后监工单轮输入仍显著高于摘要方案"，就跳到了引入 GPU 依赖。**这是优先级判断缺少前提，不是技术错误。**

## 六、被删掉的实现细节（建议原样回退）

这部分是本次改版的隐性损失：文档变长了，可编码的规格变少了。按严重度排序：

1. **`output_read` 的越权校验**（.bak 第 263–271 行）。删掉了 `require(rec.room == session.room)` 和 `require(rec.owner_session in (session.key, 'host'))`，而新验收用例 1（第 799 行）仍然要求"执行者越权读取其他会话输出时被拒绝"。**规格被删、验收还在。**
2. **E6 的 `normalize(provider, raw)`**（.bak 第 435–447 行）。删掉了 codex 累计值取差分、claude/deepseek/gemini 字段映射。这恰恰是当初 token 数算错的根因。新 E6 的 `report()` 只剩聚合，而聚合依赖的 `avoided_tokens` 字段不存在。**E6 现在是一段跑不起来的报表。**
3. **E5 的 `SCALE` / `cap_for` / `after_reply` / `reminded` 幂等**（.bak 第 403–418 行）。删掉后，"每成员每类只提醒一次"和容忍度缩放都没了机制，但验收用例 6 还在测 180 字。
4. **E4 的 `cell()` 转义规则与解码提示**（.bak 第 375、387–388 行）。尤其是 `"name[N]{a,b,c}: 表示 N 行、字段依次为 a,b,c 的表格。"` 这句——**没有它，监工模型从没被告知过这个格式，却要读它**。这是 E4 唯一的安全绳。
5. **E3 关于原生会话无法检测的坦白**（.bak 第 362 行）。新 E3 只保留了 API 路径检测，把"Codex/Claude 由各自运行器拼接请求、宿主无法逐字节检测，只能靠 A1 缓存比例推测"整段删了。删掉之后，第 708 行的"100% 吃到缓存折扣"看起来像是有保障的——实际覆盖不到 91.6% 的 token。
6. **E2 的 `MATERIALS` 挂接与三个适配器接线**（.bak 第 321–332 行）。删掉了 `MATERIALS['propose']` / `MATERIALS['review']` 的具体替换，也删掉了"Codex 加入 dynamicTools / Claude CLI 加入 room MCP / API 加入工具循环"——而这正是三个适配器没有统一读取能力时最难的一段。

```python
# 只拒绝，不改写；压缩交给 E1 的 present()
DENY = [
    (r'\bcat\s+\S+\.(log|json|out)\b.*\|\s*(head|tail|less|more)\b', 'redundant_pager'),
    (r'\bfind\s+/\s', 'whole_disk_search'),
    (r'\bgit\s+log\b(?![^|]*(-n|--max-count))', 'unbounded_git_log'),
]
def pre_tool_guard(command):
    for pat, tag in DENY:
        if re.search(pat, command):
            return None, tag            # None = 拒绝执行，回一句“请加 -n 100 后重试”
    return command, None                # 其余原样放行，语义绝不改变
```

要点：**返回原命令或拒绝，二者只选其一，绝不返回"另一条命令"。** 如果一定要保留 `cat` 优化，限制为"整条命令精确等于 `cat x.log`"（无管道、无重定向、单文件），并且在解析失败时回退原命令。默认关闭。
