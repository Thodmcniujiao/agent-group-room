## 二、会直接崩的 6 处(按严重度)

### F1 `@headroomlabs/headroom` 与 `@context-mode/mcp` 都不存在

```
GET https://registry.npmjs.org/@headroomlabs%2Fheadroom  → 404
GET https://registry.npmjs.org/@context-mode%2Fmcp       → 404
```

Headroom 官方 README 明确写了两件事,方案的写法同时违反:

> `npm install headroom-ai` — TypeScript SDK only — no CLI
> The `headroom` CLI ships only in the PyPI package. The npm `headroom-ai` package is the TypeScript SDK … and provides no `headroom` command.

也就是:**CLI 只随 PyPI 包发布**。正确写法是 `pip install "headroom-ai[all]"`(或 `uv tool install`),不是 npm。

### F2 Headroom 的两个请求头是发明的,而错误后果是 401

方案的胶水核心是:

```python
default_headers={
    "X-Headroom-Target-URL": original_base_url,
    "X-Headroom-Compression-Mode": "smart-ccr"
}
```

在官方 README 全量文本里 `X-Headroom` 与 `Compression-Mode` 各出现 **0 次**。官方给出的目标上游机制是环境/参数级:

> For a third-party OpenAI-compatible provider (DeepSeek, Together, OpenRouter…), pass `--openai-api-url https://api.deepseek.com/v1` — or set `OPENAI_TARGET_API_URL` before wrapping — otherwise **your provider key is sent to OpenAI and rejected with `401 Incorrect API key provided`**.

这正是方案会踩的坑:头被忽略,代理按默认上游走 OpenAI,DeepSeek/Gemini 的 key 被拒。**错误信息看起来像 key 配错了,实际是把流量发错了地方。**

### F3 Context Mode 的工具名和 env 全是另一个项目的形状

方案写的 `sandbox_bash / sandbox_read / sandbox_search` 和 `CONTEXT_MODE_MAX_OUTPUT_TOKENS / CONTEXT_MODE_ENABLE_FTS5`,在官方 README 里都是 0 次出现。真实接口:

```bash
npm install -g context-mode          # 包名就是 context-mode
claude mcp add context-mode -- npx -y context-mode   # MCP-only 路径
```

工具是 6 个 `ctx_*`。更要命的是,**98% 那个数字只在有 hook 的客户端上成立**;官方自己的表写着 "With Hooks ≈98% / Without Hooks ≈60%",而方案走的 `session.register_dynamic_tools(...)` 属于 MCP-only(≈60%),并且需要模型自愿改用它——官方明说这需要 routing 文件,否则"模型仍会用原生 Bash"。

所以 `# 将其提供的沙箱工具直接绑定到执行者上下文，取代无保护的原生 Bash` 这句在机制上不成立:**注册 MCP 工具不会移除原生 Bash**。

### F4 Aider RepoMap 的 10 行胶水有四重错

我把上游 `aider/repomap.py` 拉下来逐行核对:

```python
def __init__(self, map_tokens=1024, root=None, main_model=None, io=None, …)
def get_repo_map(self, chat_files, other_files, mentioned_fnames=None,
                 mentioned_idents=None, force_refresh=False):   # ← 没有 max_map_tokens
    if self.max_map_tokens <= 0: return
    if not other_files: return                                   # ← other_files 为空直接 return None
```

1. **`get_repo_map(..., max_map_tokens=…)` → TypeError**。该参数不存在(构造函数里叫 `map_tokens`)。
2. 即使去掉这个参数,`other_files=[]` 会命中 `if not other_files: return`,**永远返回 None**。
3. 即使补上 other_files,`main_model=None` 时 `self.token_count()` 会调 `self.main_model.token_count(...)` → **AttributeError**。
4. `chat_files` 的语义是"已在上下文里的文件",会被 `to_tree` 主动排除;方案把 `focus_files` 传进去,如果这些文件没有随消息一起发出,它们会**从地图里消失**。

另外 `RepoMap.__init__` 会在项目根目录建 `.aider.tags.cache.v4`(diskcache/SQLite),会污染仓库,需要进 `.gitignore`;`aider-chat` 还会拖进 litellm、tree-sitter、pygments、networkx、diskcache 一整套重依赖。

正确写法(附最小可用):

```python
from aider.repomap import RepoMap
from aider.io import InputOutput

class _Tok:                      # 只用于 token 计数,避免引入 litellm/网络
    def token_count(self, text): return max(1, len(text) // 3)

def generate_repo_map(root, focus_files, budget_tokens=2000):
    io = InputOutput(yes=True)
    rm = RepoMap(map_tokens=budget_tokens, root=root, main_model=_Tok(), io=io)
    others = [p for p in walk_source(root) if p not in set(focus_files)]
    if not others: return ""
    return rm.get_repo_map(chat_files=list(focus_files), other_files=others) or ""
```

> 顺带说一句:这段代码仍然只有 10 行,但它和方案里的 10 行**没有一行相同**。这就是"直接引用"的真实成本——省掉的是算法,不是对齐成本。

### F5 TOON:导入名错,而且对嵌套账本用全量 dumps 方向反了

`pip install toon-format` 对,但模块是 `toon_format`,方案写 `import toon`。

更实质的问题:TOON 官方给的是 "100 uniform records take **38%** fewer tokens than compact JSON" 且 "**Deeply nested or irregular data gains less**"。上一版的 E4 只编码**规整的对象数组**,并保留"取更短者"的比较;这一版的 I5 改成 `toon.dumps(ledger_dict)` **无条件序列化整个嵌套账本**——在最不该用 TOON 的形状上用它,而且删掉了比较回退。

建议:

```python
import toon_format as toon
def format_ledger_payload(ledger):
    parts = []
    for k, v in ledger.items():
        js = json.dumps({k: v}, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
        if is_uniform_list(v) and len(v) >= 3:
            try:
                t = toon.dumps({k: v})
                if len(t) < len(js) * 0.95: parts.append(t); continue
            except Exception: pass
        parts.append(js)
    return "\n".join(parts)
```

并且**必须**在监工角色指令里补回解码提示(`name[N]{a,b,c}:` 表示 N 行表格)——上一版有这条,这一版删了。没有它,监工模型从没被告知过这个格式。

### F7 `sources.lock.json` 的扩充会毁掉这个文件的可信度

现有文件是有纪律的:

```json
"deepseek-as-subagent": {
  "commit": "7e54026392f85ccfc796f947faf9ffac3968a49e",   // 40 位 SHA
  "installed": true, "note": "hash-locked dependencies, non-editable wheel", "repository": "…"
},
"codex-review-server": { "commit": "6caed1d…", "installed": false, "note": "inspected only; POSIX-specific…" }
```

它同时表达两件事:**锁到 commit**,以及**区分"已装"和"只调研过"**。

新增的 7 条把这两条纪律都丢了:`"version": "latest"`(lock 文件里写 latest 等于没锁)、无 `commit`、7 项一律 `"installed": true`。

而本机实测:

```
npm ls -g --depth=0  →  @google/gemini-cli, agent-browser     (没有 headroom / context-mode / ccusage)
pip list             →  无 aider / toon_format / headroom
requirements.txt/lock → 无相关条目
11434 / 8787 端口     →  均未监听
ollama               →  未安装
```

**7 个 `installed: true` 全部为假。** 锁文件一旦可以说假话,以后就不能拿它做审计依据了。

建议改成:

```json
"headroom": {
  "repository": "https://github.com/headroomlabs-ai/headroom",
  "package": "headroom-ai", "pin": "==0.41.0", "commit": "<tag 对应 SHA>",
  "installed": false, "verified_at": "2026-10-22",
  "entrypoints": ["headroom proxy --port 8787"],
  "note": "PyPI 包含 CLI;npm headroom-ai 仅 TS SDK,无 CLI"
}
```

## 三、架构性问题(不是笔误,是设计)

### A1 代理只能覆盖 8.4% 的流量,而方案以为覆盖了全部

`configure_provider_client()` 改的是**宿主自己发起的 API 客户端** `base_url`。但主方案 A1 的基线是:

| 身份 | 输入 token | 占比 | 调用方式 |
| --- | --- | --- | --- |
| 监工(GPT + Gemini) | 1,123,542 | 56.9% | Codex / Gemini CLI **原生会话** |
| ChatGPT 成员 | 685,011 | 34.7% | **Codex CLI 原生会话** |
| Claude 成员 | 111,956 | 5.7% | Claude CLI 原生会话 |
| Gemini 成员 | 54,809 | 2.8% | API / CLI |

原生 CLI 的网络层在 CLI 进程里,宿主的 `base_url` 改不到。**I1 实际覆盖的上限是 8.4%,而它被画在 5 级 Pipeline 的每一个入口上。**

Headroom 自己给了正确解法,方案没用:

```bash
headroom wrap codex      # Codex ✅
headroom wrap claude     # Claude Code ✅
```

代价是 `wrap` 会启动代理、**安装 Serena**(代码语义导航)并把它注册进 `~/.claude.json`、还可能改写 CLI 配置(`headroom unwrap` 才撤销)。这意味着成员的工具集合会变——又是一个"每个成员多带一套 tool schema"的隐藏开销,而上一版专门论证过要避免这件事。这一步需要单独评估,不能当"一行重定向"。

### A2 四套记忆系统叠加,没有仲裁规则

| 系统 | 记忆能力 | 与其它重叠处 |
| --- | --- | --- |
| S1/S2 自述摘要 | 成员自述摘要,作者可追溯 | 主方案 C1 的组包 |
| Headroom | **cross-agent memory**,跨 Claude/Codex/Gemini,自动去重 | 与 S1/S2、CoMem、Claude-Mem 全部重叠 |
| CoMem | 行动一致性记忆块 | 同上 |
| Claude-Mem | 跨会话 observations + Chroma | 同上 |

Headroom 的 README 直接把 cross-agent memory 列为主功能(不只是压缩)。四套记忆各有各的 store、TTL、注入时机,职责表里没有任何一行说明**谁的记忆优先、冲突时听谁的、过期怎么清**。

这不是"胶水层",这是把复杂度从代码搬到了运行时。上一版 §5.4 我提过的归属问题在这里放大四倍:除了 S1/S2,其余三套产出的都是**宿主或第三方模型对成员发言的二次综述**,既不是原文也不是作者自述,而它们都会进入监工的上下文——也就是算共识的那一方的输入。

### A3 治理不变量被破坏了两处

**(a) 执行者获得任意代码执行 + 网络访问。**
`ctx_execute` / `ctx_batch_execute` 按官方说法"run arbitrary code and still inherit the process's filesystem access… treat approving any execution tool as approving arbitrary code";`ctx_fetch_and_index` 则会主动发网络请求。主方案给执行者的能力面是 Bash + Read(在 `tool_child_env.py` 的约束下),现在等于扩到了"任意代码 + 任意 URL",而 `ctx_fetch_and_index` 是一条现成的数据外泄通道。文档里没有任何一句限制它只给执行者、不给讨论成员。

**(b) 记忆块没有任何"不可作为表态/证据"的标注。**
S1 之所以安全,是因为它标了"作者自述摘要"并在第 107 行声明不可作为批准/表态/证据。现在 CoMem 记忆块、Claude-Mem observations、Headroom cross-agent memory 三条通道都会向成员/监工注入文本,全部没有归属标注,也没有版本绑定。主方案 B2 让批准绑定 `(plan_id, version, sha256)`;这些记忆可以跨版本存活。

### A4 把"可测"这件事一起删掉了

- 上一版的 E3(前缀断点检测 + 原生会话无法逐字节检测的坦白)整段消失。现在只剩一句"Headroom … **100% 保护**云端 Prompt Cache 命中率"。Headroom 的 CacheAligner 原文是 "flags volatile content… **never rewrites prompts**"——它只会**标记**易变内容,不提供 100% 保证;而且它覆盖不到原生会话里由 CLI 自己拼的请求。
- 上一版的 E6 `normalize(provider, raw)` 被 ccusage 取代。但 ccusage 读的是 CLI 的本地日志,**没有 room / role / member / composition 维度**——而 A1 的全部价值就在这几个维度上。I7 的验收标准写成"与 CLI 终端显示完全一致",这只能证明"同一个工具输出一致",证明不了归因。
- 结果:**7 个集成,零个可归因指标**。文档同时删掉了净节省核算、四维闸门、建议顺序、以及第 1 部分(S1–S3)的全部验收用例。第一部分代码没改,但它的验收没了。

### A5 "零重写"命题的自反

> "为什么绝不自己在宿主里写正则与自制算法去模仿开源项目?…手写极易造成…不可逆的数据损坏。"

这个论证是对的,但它推出的是"不要重写**算法**",不是"不必对齐**接口**"。而我在 §2 找到的 9 处错误,全部落在胶水层,没有一处落在算法层。**风险没有消失,只是从"算法写错"搬到了"接口写错";而接口写错的失败更隐蔽——它往往是静默无效(env 变量被忽略、请求头被忽略)或 401/None 这种看起来像别的问题的症状。**

正确的表述应该是:

> 不重写算法;**但每一处胶水都必须对着上游源码或官方 README 写,并有契约测试**。

## 四、硬件前提不成立

方案三处写"本地 **RTX 5090(32GB 显存)**"。本机实测:

```
nvidia-smi  →  NVIDIA GeForce RTX 5080, 16303 MiB      (16GB,不是 32GB)
GPU 列表     →  RTX 5080 + AMD Radeon 集显 + MuMu 虚拟显示适配器
```

16GB 不是不能跑 4B,但方案给的那条命令会当场失败:

```bash
python -m vllm.entrypoints.openai.api_server \
    --model horizon-llm/CoMem-Qwen3-4B-ICML2026 \
    --port 11434 --gpu-memory-utilization 0.25 --max-model-len 32768
```

1. `0.25 × 16GB = 4GB`,而 vLLM 默认 bf16 加载 4.4B 权重约 **8.8GB** → 启动即 OOM。
2. vLLM **没有官方原生 Windows 支持**(Linux / WSL 为主),这台机器是 Windows。
3. 模型 ID 不存在(F6)。
4. `11434` 是 Ollama 的默认端口,拿它给 vLLM 用会和将来的 Ollama 冲突。

5080 16GB 上的可行路径:

```bash
# 1) 量化后约 2.5–3GB,留足 KV cache
huggingface-cli download YWZBrandon/summary-sft-qwen3-4b --local-dir ./comem-hf
python convert_hf_to_gguf.py ./comem-hf --outfile comem-f16.gguf
llama-quantize comem-f16.gguf comem-q4km.gguf Q4_K_M
# 2) Ollama 加载,上下文从 8K 起
ollama create comem4b -f Modelfile      # FROM ./comem-q4km.gguf / PARAMETER num_ctx 8192
```

并且不要把 8 秒当硬超时:4B 模型首载 + prefill + 生成的 P95 在消费级卡上会明显超过 8 秒,而 `except: return build_fallback_summary(...)` 会把所有超时变成静默降级——你永远不知道它到底跑没跑。至少改成:启动时预热、超时 30–60 秒、超时事件计数并写进 A1、用上一版记忆兜底(这才是 CoMem 论文的 k-step-off,同步 `await` 不是)。

### R3 I2 降级为"只给执行者,且先跑通 MCP-only"

### R6 恢复被删的三样东西

1. **S1–S3 的验收用例**(第一部分的代码没变,验收不该消失);
