# 并行架构视角下的 Agent Group Room：可行性边界与“强强联合”的设计条件

## 0. 结论先行

**第一，它当前不是“多智能体并行系统”，而是“集中调度的分层黑板＋单写者事务”。** 监工串行决策，成员只读并行，执行者独占写入，宿主独立验收。上一轮那六个预算参数，其实就是这套并行模型的资源约束：软预算是一个超步的地址空间，输出预留在同一窗口内切分，工具续轮是单次发言的指令窗口，监工轮数是调度器的时间片，轮转是检查点。

**第二，“强强联合”的收益不来自把 k 个强模型并排放，而来自四个可分离的条件**：能力异质、错误去相关、任务低耦合、验证可外包给确定性 oracle。缺任何一项，并联得到的只是“更贵的单模型”，而不是更强的系统。

**第三，学术上可行，但命题必须改写**：从“多 agent 是否更强”改为“在什么任务结构、成本函数与验证条件下，并行协作的净收益为正”。这个项目恰好具备做这类研究的稀缺条件——provenance、隔离、恢复、验收都被做成了可观测对象。

## 1. 事实基线：映射到并行计算模型

```
                    ┌──────────────┐
                    │  监工 (×1)    │  串行：每轮一次 LLM 调用 + 控制校验
                    └──────┬───────┘
         ┌─────────────────┼─────────────────┐
         │   ask(parallel=true) → barrier     │
    ┌────▼────┐       ┌────▼────┐       ┌────▼────┐
    │ 成员 A  │       │ 成员 B  │       │ 成员 C  │   只读，共享同一 boundary 快照
    └────┬────┘       └────┬────┘       └────┬────┘
         └─────────────────┼─────────────────┘
                    ┌──────▼───────┐
                    │  执行者 (×1)  │  单写者：契约 + allowed_paths + 前后哈希
                    └──────┬───────┘
                    ┌──────▼───────┐
                    │   宿主验收    │  串行：测试、哈希、范围、恢复记录
                    └──────────────┘
```

| 并行计算概念 | 本项目对应物 |
|---|---|
| BSP 超步 / barrier | 监工一轮；`asyncio.gather` 汇合所有并行发言 |
| 快照隔离（snapshot isolation） | 并行发言共享同一 `boundary`，看不到同轮他人回复 |
| 读写一致性 | 串行发言 `boundary=None`，可读到上一人刚说的话 |
| 共享日志 + 私有缓存 | append-only 群消息 + 每会话 cursor/branch/native history |
| 乐观并发控制（OCC） | workflow `revision`，冲突重试三次 |
| 单写者 / 串行化调度 | 每项目一个执行者，`project_busy` 项目级互斥 |
| 事务提交 + 约束检查 | 方案哈希、批准、契约、allowed_paths、文件哈希、宿主验收 |
| 检查点与恢复 | 会话归档、recovery records、`started` 标记 |
| at-most-once 语义 | 已启动契约不自动重派，必须宿主核对 |

这套结构在学术谱系上更接近 Hayes-Roth 的**黑板系统**（共享数据结构 + 知识源 + 控制器）加上 Smith 的**合同网**（监工招标，执行者接单），而不是对等市场或多智能体辩论场。集中调度的优点是全局一致性和可审计性；代价是根节点成为瓶颈，且并行度受单一控制器限制。

有一个细节值得肯定：并行只读发言共享快照、串行发言读己之所写，这是数据库里成熟的隔离级别选择，作者显然是按一致性而非“让 agent 自由聊天”来设计的。`counted_round` 保证一轮并行只消耗一次讨论容忍度，也避免了“并行即多轮”的记账错误。

## 2. 并行度的数学：为什么“人多”不等于“快”

BSP 模型下，第 r 轮的时间近似为

```
T_round ≈ L_sup + max_i w_i + V
T_total ≈ R · (L_sup + max_i w_i + V)
```

其中 `L_sup` 是监工一次决策的延迟（一次前沿模型调用加 JSON 校验），`w_i` 是成员 i 的单轮工作时长，`V` 是验收与宿主检查，`R` 是轮数。关键含义是：

**当 `max_i w_i < L_sup` 时，扇出是负收益。** 并行省下的成员时间，还不够监工多等待一轮的调度开销。设 `L_sup=20s`、`w=30s`、`n=4`：并行段 30s 对比串行 120s，看似 4 倍；但每轮固定 20s 监工，6 轮总时间约 `6×50=300s`，串行是 `6×140=840s`，实际 2.8 倍。若 `w=10s`（短问答），则只有 2 倍左右；若并行带来更多信息、更多纠错轮，`R` 上升，收益还会被吃掉。

Amdahl 给出上界：

```
S(n) = 1 / ((1-p) + p/n)  →  1/(1-p)
```

`p` 是可并行比例。本项目里 `p` 主要只有“只读发言”这一段，监工决策、写、验收都在串行段，所以 `n→∞` 的加速比很快就封顶。Gustafson 的乐观版本要求问题规模随 n 增长（更多审查维度、更大语料），但 token 成本线性增长，收益递减。

**推论：真正的加速来自缩短关键路径，而不是增加成员数。** 可动的三个量是 `R`（减少轮数、异步化）、`L_sup`（分层监工、用小模型做例行调度）、`V`（并行测试、增量验收）。这也解释了为什么 Anthropic 的报告里，收益最大的场景是“广度优先、可并行检索”的任务——那里的 `p` 接近 1，且 `w_i` 远大于调度开销。

## 3. “强强联合”的形式条件

### 3.1 复制与分解是两种不同的东西

设成员 i 在任务 T 上的成功率 `p_i`，错误相关系数 `ρ`。多数投票的正确率在等相关的潜变量模型下是

```
P_correct = Φ( μ√n / √(1 + (n-1)ρ) )
```

`ρ=0` 时随 n 增长（Condorcet 陪审团定理的条件）；`ρ→1` 时退化为单成员，**再多的强模型也不增加信息**。同一批前沿模型共享互联网语料、相似的 RLHF 偏好和相似的提示偏差，`ρ` 通常不低。这就是“同质强模型并联只买到方差缩减”的定量版本。

分解则是另一回事。若 `T = f(T₁,…,T_k)`，则

```
P_success = (∏ p_i) · p_merge
```

分解把 1 个失败点变成了 k+1 个失败点。**分解不是免费的午餐**：它只有在“子任务能交给更合适的成员”或“每段都能被独立验证纠错”时才划算。由此得到本文的核心区分：

> **复制（replication）买的是稳定性，分解（decomposition）买的是能力上限。**
> “强强联合”属于后者，但工程上经常误做成前者。

集成学习的 ambiguity decomposition 给出了同一结论的另一面：`E_ensemble = Ē − Ā`，泛化误差等于平均个体误差减去分歧度。**收益来自分歧，而不是来自个体更强**；一个高度一致的强模型群体，分歧度 `Ā` 很小，集成就没有空间。

### 3.2 四个必要条件

1. **异质（heterogeneity）**：成员在不同子任务上的能力差异，必须大于协调成本。跨厂商模型（GPT / Claude / Gemini / DeepSeek）在训练数据、工具协议、失败模式上确实不同，这是本项目最大的结构性资产。
2. **低耦合（low coupling）**：子任务之间的必要通信量远小于子任务本身的计算量。否则通信通道成为瓶颈（Yao 的通信复杂度视角），并行退化为“轮流汇报”。
3. **可验证（verifiability）**：每个子任务至少有一个廉价、独立的检查。没有 oracle，聚合只能退化为“对合理性投票”，而 LLM-as-judge 已知有位置、长度和自我偏好偏差，且与被评模型错误相关。
4. **非对称（asymmetry）**：生成者与验证者必须在模型、上下文或工具上不同源。让同一个模型“再检查一遍”，等于把 `ρ` 设为 1。

一个常被忽视的红利是**上下文压缩**：并行子代理的真正价值，是各自在私有窗口里把大语料压成有界报告，主控只读报告。这本质上是率失真（rate–distortion）问题——每份报告的 token 数是码率，丢失的细节是失真；最优分配应让各代理的边际失真/ token 相等。Anthropic 的 90.2% 提升与 15× token 成本，正是这笔交易的定价。

### 3.3 验证瓶颈：排队论视角

把验收看成单服务台，生成端并行加宽只会提高到达率 `λ`。M/M/1 的等待时间

```
W_q = ρ_s / (μ(1-ρ_s)),   ρ_s = λ/μ
```

当 `ρ_s→1`，等待时间发散。**当验证成本超过生成成本时，增加并行宽度会降低有效吞吐**——这是很多 MAS 演示“看起来并行、实际更慢”的隐藏原因。本项目的宿主验收（跑测试、算哈希、查范围）是单服务器，所以它天然是并行度的上限。

## 4. 诊断：三个串行段与四个结构性风险

| 瓶颈 | 代码证据 | 后果 | 改进方向 |
|---|---|---|---|
| 监工串行 | `supervisor_loop` 每轮一次 LLM + 校验，`max_steps` 封顶 | 关键路径 = R×模型延迟；根节点单点 | 分层监工、异步事件驱动、投机执行 |
| 写路径单点 | `execute` 只允许一个 agent；`project_busy` 项目级互斥 | 写吞吐恒为 1；模块化仓库的并行度被浪费 | 分区写 + worktree + 宿主合并 |
| 验收串行 | `verify_commands` 顺序 `for` 循环 | 长测试套件成为尾部延迟 | 并行测试、缓存、增量验收 |
| 上下文复制 | 每个成员独立会话；并行共享 boundary | 通信量 O(n·|C|)，成本随宽度线性涨 | 前缀缓存、claim 图、增量广播 |
| 投票相关性 | review/vote 同一材料、同一提示结构 | 虚假共识；一致地错 | 隔离首轮、异质评审、证据绑定 |
| 调度无成本模型 | `parallel` 由监工自由裁量，无 DAG、无预估 | 并行可能负收益，且不可复现 | DAG + 成本估计 + 自适应宽度 |
| 缺基线测量 | 有用量记录，无同任务单 agent 对照 | 无法证明“联合”的净收益 | 配对实验、成本归一化指标 |

还有两个更微妙的架构问题：

**并发正确性靠约定，而非锁。** 并行 `ask` 的多个协程在 `await` 点交错修改同一个 `self.state`（evidence 追加、votes 写入、discussion_rounds 自增），目前靠单事件循环、互不相交的键和 `save()` 的冲突合并来保证。这在 asyncio 下成立，但一旦换成线程/多进程，或者未来引入真正的并行工具调用，就会退化成数据竞争。学术上这是一个“协作式调度 + 共享可变状态”的模型，需要显式的不变式（invariant）而不是默认安全。

**“并行”目前是监工的一个布尔开关，而不是从任务结构推导出来的。** 这意味着并行决策不可解释、不可复现、无法做消融实验。要研究“应该如何并行”，第一步是把 `parallel: true` 换成一张带依赖的任务图。

## 5. 设计建议：从“对话并行”到“可验证数据流”

**P1｜DAG-first 调度。** 监工输出带依赖的任务图（节点 = 子任务、owner、验收、预估成本），宿主用 list scheduling 执行就绪节点，只在依赖处设 barrier。这把 BSP 的全局同步换成数据流，`R` 从“监工轮数”变成“关键路径长度”。映射点：`supervision.validate_control` 增加 `plan` 动作；`coordination.supervisor_loop` 改为事件驱动的执行器。

**P2｜读并行、写分区。** `allowed_paths` 已经是天然的分区键。让 K 个执行者在独立 git worktree 中并行，各自跑本分区的验收；宿主负责合并并跑全量测试，冲突则中止并升级。形式化地说：**分区内可串行化 + 宿主提交时全局可串行化**。这是把数据库的两级锁思想搬进代码协作，也是当前“单写者”约束最自然的放宽路径。

**P3｜投机执行（speculative execution）。** 在评审进行时先启动最可能的方案，评审否决则取消。收益条件是 `评审延迟 > 执行延迟`；成本是浪费的 token。项目已有 stop/cancel 和契约哈希，工程上可行。

**P4｜独立验证层。** 验证者只拿产物、规格和测试结果，不看生成者的推理；优先用确定性 oracle（测试、类型检查、diff、schema），LLM judge 只做补充并校准假接受率。项目的宿主验收已经是正确方向，应把它从“执行后检查”扩展为“每个并行分支的准入条件”。

**P5｜证据化通信。** 广播 `claim(id, hash, evidence_ids, confidence)`，而不是全文；需要细节时按 message_id 回取。项目已有消息 ID、摘要目录和交接包，缺的是一张显式的 claim 图，让分歧定位到“哪条断言、哪份证据”，而不是“谁的措辞”。

**P6｜自适应宽度与预算。** 以“每 token 的可验证进展”为信号，边际收益等于边际成本时停止加宽；给每轮、每任务设 token 预算（现有软预算可扩展为并行分支预算）。这把 `max_steps` 从固定时间片变成在线最优停止问题。

**P7｜失败语义。** 保持 at-most-once（副作用不可幂等，自动重试会破坏安全性）；为合并阶段加 saga 式补偿；工具调用加幂等键。项目在“已启动不重派 + 宿主核对”上已经比多数 MAS 严谨，应把它写进论文而不是当作实现细节。

## 6. 可检验假设与实验设计

| 编号 | 假设 | 预期 | 关键指标 |
|---|---|---|---|
| H1 | 等成本下，异质模型组合优于同质组合 | 成立，且在可验证任务上更明显 | pass@1、cost-normalized pass |
| H2 | 错误相关 ρ 高的任务上，投票无增益 | 成立；ρ 是调节变量 | ρ̂（配对结果的相关矩阵） |
| H3 | 异步数据流比 BSP 墙钟更短，但一致性事件更多 | 成立；需要宿主仲裁 | wall-clock、冲突率、回滚次数 |
| H4 | 分区写提升模块化任务吞吐，耦合任务冲突率超线性上升 | 成立 | 吞吐、merge conflict rate |
| H5 | 验证成本 > 生成成本时，加宽并行降低有效吞吐 | 成立（排队论） | 端到端吞吐、验收队列长度 |

度量建议：`speedup = T(1)/T(n)`（等质量下）、`coordination overhead = (监工 + 验收 token)/总 token`、`tokens per verified artifact`、`verification coverage`（有独立 oracle 的交付比例）、`ρ̂`（同一任务上两两成员的对错相关系数）。基准要覆盖可验证与不可验证两端：SWE-bench 类（代码）、数学（可验证）、深度检索（读多、可并行）、写作（不可验证，作为对照）。统计上必须配对、多次采样、报告置信区间——LLM 的非确定性会让单次对比失去意义。

## 7. 可行性判断

- **安全性/正确性：高。** 隔离、契约、哈希、验收、恢复语义比多数已发表的 MAS 严谨；`at-most-once` 的选择在副作用场景下是理论上正确的。
- **效率/并行性：中低。** 集中调度与单写者是天花板；当前并行度由监工的布尔开关决定，缺乏成本模型。
- **学术价值：高。** 它把“协作”从提示词工程变成了可观测的运行时对象——这正是研究并行协作所需要的实验台。

三个开放问题，按重要性排序：

1. **如何在线估计任务的可分解性与成员错误相关性？** 这决定了该复制还是该分解，是调度器的前置输入。
2. **语义合并能否由 oracle 裁决，而不是由模型仲裁？** 文本 merge 是成熟的；语义 merge（两个分支都改了同一抽象）目前只能靠测试覆盖，测试不足时就是不可判定。
3. **预算约束下的最优停止与调度是什么？** 把 `max_steps`、工具续轮、token 预算统一成一个受约束的优化问题。

最后回到“强强联合”这个提法本身。这个项目已经证明了一件重要的事：**强强联合的敌人不是模型不够强，而是协调成本、错误相关性和验证瓶颈。** 它的架构在“安全地联合”上走得比“高效地联合”远。下一步的研究命题，不是让更多 agent 同时说话，而是：

> **把多智能体系统当作一个带验证的并行运行时来设计——用任务图取代对话轮次，用分区写取代全局单写者，用独立 oracle 取代模型自评，用成本感知的调度取代监工的自由裁量。**

这四件事，恰好也是并行计算六十年里反复验证过的四件事。
