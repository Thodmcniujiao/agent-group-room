# Agent Group Room 上下文调查与改造计划

调查日期：2026-10-21。状态：调查与设计，尚未实施。

本次依据四家官方文档及本机源码检查制定方案；没有启动模型推理、修改运行逻辑、重启桌面程序或发布到 GitHub。协议可用性目前只做了离线 schema 核对，正式接入还需小规模验证。

## 1. 已确认的目标

采用“群内原始消息共享 + 各 Agent 独立会话 + 可指定的执行者”架构。

- 讨论成员直接收到其他成员的公开原始答复，监工负责安排与监督合作方式。
- 每个协作室可以指定一名执行者，默认选择 DeepSeek，也可以改成其他成员；身份与服务商、模型分开配置。
- **执行者是用户明确指定的例外：只接收监工整理的执行要求，不接收其他成员的群聊上下文。**它仍可读取任务允许的项目文件、项目规则、自己的工具结果与执行记录。
- 执行者的最终答复和执行证据可以发布回群，供监工与讨论成员直接读取。
- 不给讨论成员预设固定的计划、评审分工；其合作方式仍由用户定义。
- 全部设置按协作室保存，沿用现有“Agent 连接库 / 协作室成员”两层结构。

这里的“共享上下文”指共享可公开的消息与证据。模型自己的原生工具过程、协议签名和私有推理状态，保存在该身份的独立会话中，不混入别人的会话。

## 2. 当前程序的实际问题

程序已有一部分原始答复转交，不能说当前全靠监工转述。主要问题是共享范围、截断方式和会话生命周期没有统一。

| 位置 | 已核实的行为 | 影响 |
| --- | --- | --- |
| gui/store.py：Store.history | 只取最后 20 条；每条最多 4,000 字符；合计再取末尾 14,000 字符 | 旧消息消失，长答复中间内容丢失，按字符截断并不等于按 token 控制 |
| gui/store.py：Store.update | 写入正文时截到 100,000 字符 | 部分超长原文在持久层就可能丢失 |
| gui/orchestrator.py：supervised | 每次新任务从空 records 开始 | 同一群上一轮协作知识不能稳定延续 |
| 同上：ask | 监工可用 share_previous 决定是否共享；单条证据截到 16,000 字符，拼接记录再截到 35,000 字符 | 可见性受调度结果控制，多次截断使原文不完整 |
| 同上：一次 ask 的多个成员 | prompt 在循环外构造，即使串行调用，也复用同一份旧记录 | 串行调用不代表后一个已经看到前一个本轮的答复 |
| gui/engines.py：cli_reply | ChatGPT 使用 --ephemeral；Claude 使用 --no-session-persistence，每次新进程接收一段文本 | 没有按群和身份续接自己的原生会话 |
| 同上：deepseek_reply | Gemini / DeepSeek 共用 OpenAI 兼容请求，system + 单条 user 大文本，max_tokens 固定 8,192 | 未保留结构化多轮消息和完整原生响应块 |
| gui/orchestrator.py：execute_supervised | 编码主要接收监工契约；Gemini 也走 DeepSeek MCP 执行循环 | 不能只改普通聊天路径，否则更换执行者时仍不符合各家协议 |

另查本机 deepseek_mcp：一个编码任务内部已经保留完整 assistant 消息和工具结果；但每个新任务仍从 system + task 初始化。它另有 1,000,000 的**累计运行 token 预算**及 12 MiB 历史大小限制，这些是执行器限制，不能误当成模型的单次上下文窗口。

项目快照也有字符上限，只包含部分路径、差异和指定文件，不能视为模型已经读过整个目录。

## 3. 四家的官方规则与接入结论

以下数值对应调查时本机选择的模型。它们是官方 API 规格；CLI 实际可用窗口、运行器预留与自动压缩阈值还要独立确认。以后换模型应查询对应型号，不能给一家所有模型套同一数字。

| 服务商 / 当前模型 | 官方规格 | 计划采用的上下文方式 |
| --- | --- | --- |
| ChatGPT / gpt-6.1-sol | 上下文 1,050,000；最大输出 128,000 tokens | 保留 CLI 账户登录，通过 Codex App Server 维护每群、每身份的独立 thread |
| Claude / claude-opus-5-5 | 上下文 1M；最大输出 128K tokens | 显式 session_id 续接 Claude Code 会话，由原生运行器管理自己的历史与压缩 |
| Gemini / gemini-3.8-flash | 输入 1,048,576；输出 65,536 tokens | 独立 Gemini 原生适配器，优先 Interactions API；本地保存完整多轮结构 |
| DeepSeek / deepseek-flash | 当前别名对应 V4.1-Flash-1017；上下文 1M；最大输出 384K tokens | 本地保存结构化 messages，每次请求按要求重传；作为默认执行者时只接收执行契约 |

规格来源：[OpenAI GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[Claude Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/overview)、[Gemini 3.8 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash)、[DeepSeek 模型规格](https://api-docs.deepseek.com/quick_start/pricing/)。最大输出表示允许的上限，不是计划每次申请的输出预算。

### ChatGPT

Codex App Server 提供 thread/start、thread/resume、turn/start，以及不启动生成而向已有历史追加原始项目的 thread/inject_items；也提供原生压缩与 token 用量事件。这支持“自己续会话，同时收到群内新原文”的方案。[OpenAI 官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

本机 codex-cli 0.160.0 的离线实验 schema 确认存在上述接口；用量通知含可空的 modelContextWindow。是否对当前账户完整可用尚未做生成验证。modelProvider/capabilities/read 只有部分工具能力信息，不能靠它读取窗口大小。

计划优先验证原始群消息作为外部消息注入；不支持时，将同一批原文附入下一次 turn/start。保持现有登录方式和权限限制，不因本次改造要求新增 OpenAI API 密钥。

### Claude

Claude Agent SDK / Claude Code 可以按明确 session_id 续接历史。不能使用“继续最后一次会话”的模糊方式，否则多个群共用项目目录时可能串会话。[Claude 会话管理](https://code.claude.com/docs/en/agent-sdk/sessions)

Opus 5.5 的 thinking 状态与模型、会话及其前缀有关，不能随意改写旧系统消息、工具配置或旧消息后继续重放原块。近期 Opus 模型默认还会把之前的 thinking 计入上下文，不能沿用旧模型“之前思考自动不占窗口”的估算。[迁移规则](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)、[上下文计算](https://platform.claude.com/docs/en/build-with-claude/context-windows)

计划让原生运行器管理这些块，群聊只追加新消息。讨论与编码权限集不同，若不能用已支持的原生方式安全切换，就创建独立用途会话；用公开消息或执行契约衔接。保留原生自动压缩，不通过手工剪旧 JSON 模拟压缩。[Claude Code 压缩配置](https://code.claude.com/docs/en/env-vars)

### Gemini

当前官方推荐新项目使用 Interactions API；generateContent 仍支持，但已标为 legacy。Interactions 可用 previous_interaction_id 续接服务端状态，也可用 store=false 自管完整历史。后者不能续接服务端 ID。[Interactions 官方文档](https://ai.google.dev/gemini-api/docs/interactions-overview)

计划默认采用本地历史 + store=false，避免为了续聊新增默认的云端会话存储；这不是“请求不会发送到 Google”的承诺。若以后开放云端续聊选项，应明确显示保留策略；当前文档说明存储期限按免费/付费及项目设置变化。

无状态模式须原样重传本会话完整 thought 块及相应内置工具签名。不能只提取 output_text 再拼回历史，也不能把另一位成员的回复伪装成本 Gemini 的 model 输出。[Gemini thinking 与签名](https://ai.google.dev/gemini-api/docs/thinking)

3.8 Flash 使用分开的输入和输出预算；不能套用 Gemini 4 的统一窗口计算。通过 models.get 获取型号限制，预检可用 countTokens，并以实际返回 usage 校正；完整 Interactions 结构与计数请求之间的兼容性需在原型中核对。[Gemini token 规则](https://ai.google.dev/gemini-api/docs/tokens)

### DeepSeek

Chat Completions 是无状态调用，需要重传历史。DeepSeek 的 Responses 格式也不提供 previous_response_id / conversation 服务端续聊；更换接口名称不会自动得到记忆。[多轮对话](https://api-docs.deepseek.com/guides/multi_round_chat/)、[Responses 支持范围](https://api-docs.deepseek.com/guides/responses_api/)

启用 thinking 并使用工具时，官方要求带回之前各轮的 reasoning_content；没有工具调用时规则不同。执行适配器必须保留自己的 assistant、reasoning_content、tool_call_id 和工具结果完整对应，不能只保存最终文字。它们不作为其他成员的公开群聊上下文。[DeepSeek thinking 规则](https://api-docs.deepseek.com/guides/thinking_mode/)

保留现有执行器的文件契约、写入恢复和预算约束，新增可持久化的执行会话边界。不要直接修改 site-packages；需通过受版本控制的适配层或受控依赖变更实现，并重新锁定依赖。

## 4. 消息流与执行者例外

~~~mermaid
flowchart LR
    U[用户消息与合作方式] --> L[本群公开原文库]
    L --> D[讨论成员各自会话]
    D -->|原始公开答复| L
    L --> S[监工独立会话]
    S --> C[版本化执行契约]
    C --> E[执行者独立会话 默认 DeepSeek]
    E -->|执行结果与可公开证据| L
    E --> T[任务允许的文件与工具]
~~~

### 公开原文库

消息包含稳定 message_id、本群顺序号、发送者身份、实际模型、正文块、时间、状态与内容哈希。原文完整保存；前端分页或折叠不再修改存储正文。附件先预留引用与类型，具体多媒体输入能力另按模型接入。

用户消息、公开 Agent 回复、公开执行结果进入原文库。模型原生推理块、认证材料和未公开工具记录不会因“共享”自动发布。流式中间内容保留状态，默认在完成后才参与下一轮上下文。

讨论成员的上下文由系统独立供给，取消监工随意关闭公开历史共享的 share_previous 开关。过去的原文是资料，保留作者和消息 ID；不会升级为系统权限，也不会改写成接收者自己说过的话。

### 执行者设置

在“协作室信息”内增加执行者选择，从本群成员选择，默认优先匹配 DeepSeek。若群内没有 DeepSeek，则保持待选择，不擅自新增账户或成员。仍允许不指定专门执行者；明确指定后，文件写入任务默认由该身份承接。

执行契约由监工整理，至少含目标、已定方案、必须满足的约束、允许文件/工具、验收方式、禁止事项、已知问题和本轮相对上轮的修订。宿主继续校验用户权限与文件范围；监工的总结不能扩大授权。

执行者保留自己的契约轮次、修改、工具结果和失败修复历史，不自动同步群记录，也不提供读取群原文的工具。讨论成员有新意见时，由监工形成下一版契约后送达执行者；不能在其工具调用中途偷偷替换执行要求。

执行者换人、模型/账户变化，或者讨论成员改为执行者，均创建新的执行分支。曾读过群聊的旧会话不能通过一句“忽略之前内容”变成干净执行会话。更换执行者前先核对实际文件状态和未完成写入记录，避免重复执行。

默认指派仅是本群角色设置；同一个 DeepSeek 连接也可以在另一个群作为普通讨论成员。调试控制台继续使用独立上下文。

## 5. 每个 Agent 怎样真正收到上下文

1. 持久化绑定以“协作室 + 成员/监工身份 + 角色/用途 + 连接配置版本 + 模型 + 分支”区分。共用模型或 API 密钥不等于共用会话；凭据版本用不含密钥的标识记录。
2. 调度某位讨论成员发言前，取一个确定的本群消息边界，把尚未同步的完成消息原样送入其会话。执行者走契约通道，不走该步骤。
3. 顺序讨论时，后一位默认可以读取前一位刚完成的原答复；并行讨论时，每位使用相同起点，完成后再发布给其他人。
4. 每个身份保存已确认同步位置和消息哈希，防止每轮重复附加。请求失败、进程重启或确认落盘前崩溃时，需要核对原生历史或重建分支；不能未经验证宣称“恰好投递一次”。
5. 新加入或重新加入的讨论成员，默认可访问本群公开历史；近期内容自动加载，旧内容按预算与检索补齐。移出团队暂停其会话，不删除连接密钥。
6. 用户明确要求独立提案时，采用固定快照、暂存提案、统一揭晓的轮次规则。已经读过的消息无法撤回其记忆，真正隔离的提案应建新分支。这不能由监工任意隐藏普通公开历史替代。

讨论成员与监工增加仅限当前群的只读工具：按顺序分页读取、按消息 ID 读取完整原文、搜索旧消息。CLI 通过受限 MCP 或原生动态工具接入，API 通过宿主工具循环接入；这些读取工具不赋予系统命令或文件写入能力。执行者不开放这些工具。

## 6. 长上下文、压缩与 token 成本

完整归档不等于每轮把无限历史塞进模型。计划区分“完整原文仍可读取”“本次请求实际加载”“原生会话已经压缩”三种状态。

- 将用户目标、当前合作方式、当前分工、最近关键原文优先留在活动上下文；对执行者则优先保留有效契约和自身执行状态。
- 按具体模型与运行器预算处理系统提示、工具定义、工具结果、输出和 thinking；Gemini 3.8 分开校验输入/输出，其余也按对应协议执行。无法精确计数时明确标为估算并留余量。
- 优先使用各 Agent 自己运行器的原生压缩，并记录压缩覆盖的消息范围。压缩摘要是该 Agent 的会话维护，不能变成监工替所有讨论成员统一转述群历史。
- 原文库不随压缩删除；讨论成员可用消息 ID 检索原文。原生签名历史不做任意切片；不支持安全压缩的适配器应新建分支并重建允许范围的内容。
- 单条消息过大时按可追溯片段读取，显示未加载范围；禁止再次出现静默取最后若干字符的行为。输入超限、输出截断或上下文停止需显式报告。
- 缓存保持稳定前缀和按序追加；缓存不是记忆扩容，也不意味着历史免费。Gemini 与 DeepSeek 的缓存均应以官方机制和返回用量为准。[Gemini 缓存](https://ai.google.dev/gemini-api/docs/caching)、[DeepSeek 缓存](https://api-docs.deepseek.com/guides/kv_cache/)

新群消息入库和更新同步位置本身不触发模型生成。只有轮到该 Agent 回复/执行才调用模型；初次补历史、原生压缩和重复发送历史仍可能消耗额度。执行者契约隔离可避免它反复读取长讨论过程。

## 7. 分阶段实施

| 阶段 | 内容与主要位置 | 交付判据 |
| --- | --- | --- |
| 1：原文与角色 | gui/store.py 建完整原文顺序和分页；gui/room_settings.py 增加执行者设置；迁移先备份 | 原文不再按字符丢弃；执行者按群保存；旧群/模型/密钥保留 |
| 2：统一上下文入口 | 新增上下文服务与角色路由；gui/workflows.py、gui/orchestrator.py、gui/supervision.py 改用它 | 讨论/单聊/监工都用同一原文来源，执行者只收版本化契约 |
| 3：原生会话适配 | 拆分 gui/engines.py；ChatGPT thread、Claude session、Gemini Interactions、DeepSeek messages；覆盖编码执行器 | 续聊、重启恢复、工具块往返正确，讨论与执行权限独立 |
| 4：预算与检索 | 模型能力档案、真实/估算用量、压缩事件、群原文只读工具 | 长群聊可继续且能追溯旧原文；没有静默截断 |
| 5：GUI 与验收 | 协作室角色选择、每 Agent 上下文状态、实际投递消息清单与调试信息 | 用户能检查谁收到了哪几条原文，以及执行者本轮收到哪版契约 |

第 3 阶段先做最小只读原型验证协议与本机版本，再迁入正式执行路径。后续真实测试尽量用短提示，明确记录实际调用及用量。当前这一轮只完成计划。

GUI 展示“已投递”而不是未经证实的“模型已理解”；显示最后同步消息、上下文占用与来源、压缩时间。执行者明确显示“仅接收监工执行契约”。上下文详情不显示密钥或其他身份的私有推理内容。

## 8. 验收用例

1. A 在原始答复中加入唯一编号及细节，监工不复述；B 能引用 A 的消息 ID 和原文细节，宿主投递清单与哈希也吻合。
2. 默认 DeepSeek 执行者请求中没有 A/B 原文，只含有效契约、允许的项目资料和自己的执行历史；A/B 仍直接收到它的公开执行结果。
3. 将执行者换成 Gemini / Claude / ChatGPT，执行者隔离语义一致，工具调用按各家格式完成；不能继续套 DeepSeek 协议。
4. 讨论成员切换成执行者时创建干净分支；两个群、同一服务商的两个身份、监工与成员之间都不串历史。
5. 内容超过现有 20 条 / 14,000 / 35,000 / 100,000 字符门槛后，新增原文仍可完整读回；压缩后仍能通过消息 ID 找到原文。
6. 并行提案不提前看到本轮同伴的未揭晓结果；普通顺序讨论能看到刚完成的原答复。
7. 重启、取消、超限、重试及投递确认前崩溃均有可恢复状态；不会把不完整工具调用重放成已成功，也不会无声重复执行写入。
